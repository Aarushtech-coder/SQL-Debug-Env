# SQL Debug Environment

An OpenEnv-compatible benchmark environment for evaluating agents that debug
broken SQL queries. Agents receive a schema, a buggy query, and iterative
feedback from a SQLite sandbox. They are rewarded for correctness, useful
investigation, and efficient fixes.

Built for the OpenEnv Hackathon by Meta, Hugging Face, and Scaler School of
Technology.

## What Works Today

- FastAPI server with OpenEnv WebSocket support and REST endpoints.
- Four task groups: easy syntax repairs, medium joins, hard aggregation and
  performance bugs, and security/data-leak fixes.
- Multi-step debugging commands: `SHOW_TABLES`, `DESCRIBE`, `EXPLAIN`,
  `SUBMIT_QUERY`, and `GIVE_UP`.
- Read-only SQLite execution with destructive SQL filtering.
- Reward and grader logic for correctness, efficiency, and AST complexity.
- Dynamic schema generation with Faker for randomized episodes.
- Optional LLM-backed baseline using Groq or OpenAI.
- No-key deterministic baseline for smoke tests and demos.
- Streamlit dashboard for live debugging sessions.

## Quick Start

Use a virtual environment so the same Python interpreter runs the app and tests.

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python main.py
```

The server starts at:

```text
http://localhost:7860
```

Open the API docs:

```text
http://localhost:7860/docs
```

## Smoke Test Without API Keys

In a second terminal, with the server running:

```bash
python baseline/run_baseline.py
```

If `GROQ_API_KEY` or `OPENAI_API_KEY` is not set, the baseline automatically
uses `local_solver.py`, a transparent deterministic solver for static tasks.
That verifies the environment, grader, tasks, and API without depending on an
external model.

## Optional LLM Baseline

Create `.env` from `.env.example` and set one provider key:

```bash
copy .env.example .env
```

Then run:

```bash
python baseline/run_baseline.py
```

The baseline prefers Groq when `GROQ_API_KEY` is set, otherwise it uses OpenAI
when `OPENAI_API_KEY` is set.

## Streamlit Dashboard

```bash
streamlit run dashboard.py
```

The dashboard uses the hybrid agent wrapper. For real LLM actions, set
`GROQ_API_KEY` or `OPENAI_API_KEY`. Without a valid key, the agent falls back to
simple exploratory commands, which is useful for UI smoke testing but not a
strong benchmark result.

## API Reference

| Method | Endpoint | Description |
| --- | --- | --- |
| `GET` | `/` | Environment info |
| `GET` | `/health` | Liveness check |
| `GET` | `/tasks` | List task groups and scenarios |
| `GET` | `/validate` | Self-check project configuration |
| `POST` | `/reset` | Start an episode |
| `POST` | `/step` | Run SQL or a multi-step debug command |
| `GET` | `/state` | Current episode state |
| `GET` | `/grader` | Score the current episode |
| `GET` | `/baseline` | Run the baseline against task groups |
| `GET` | `/metrics` | Runtime metrics |
| `GET` | `/telemetry/live` | Execution-time telemetry |
| `GET` | `/telemetry/ast` | SQL AST complexity telemetry |
| `GET` | `/trajectories` | Saved trajectory files |
| `POST` | `/challenge` | Generate an adversarial challenge |
| `POST` | `/mcp` | JSON-RPC style tool interface |
| `WS` | `/ws` | OpenEnv WebSocket endpoint |

## Task Design

The static registry includes 34 scenarios:

- `easy`: 11 scenarios covering syntax, column, NULL, and simple aggregation
  bugs.
- `medium`: 9 scenarios covering joins, grouping, duplicate joins, and HAVING.
- `hard`: 9 scenarios covering correlated subqueries, CTEs, aggregation level,
  and index-hostile queries over a 100k-row sales table.
- `security`: 5 scenarios covering data leaks and injection-like query patterns.

Dynamic episodes are generated by `dynamic_schema.py` with randomized table
names, columns, noisy data, and mutated SQL.

## Reward Signals

The base environment rewards:

- Successful query execution.
- Partial and exact result correctness.
- Early solutions.
- Index-friendly query plans.
- Concise SQL through an AST complexity bonus in the grader.

The multi-step wrapper additionally rewards useful investigation actions such as
`SHOW_TABLES`, `DESCRIBE`, and `EXPLAIN`.

## Project Structure

```text
sql-debug-env/
|-- main.py                    # FastAPI app, REST, WebSocket, MCP-like endpoint
|-- environment.py             # Core SQLDebugEnv
|-- multi_step_env.py          # Gym-style multi-step wrapper
|-- models.py                  # Pydantic action, observation, state models
|-- grader.py                  # Episode scoring
|-- local_solver.py            # No-key deterministic smoke-test solver
|-- dynamic_schema.py          # Faker-powered dynamic schema generation
|-- adversarial_generator.py   # Experimental mutation loop
|-- hybrid_agent.py            # Optional LLM + symbolic validation wrapper
|-- dashboard.py               # Streamlit dashboard
|-- baseline/run_baseline.py   # Local or LLM baseline runner
|-- tasks/                     # Static task registries
|-- routers/                   # REST route modules
`-- tests/test_environment.py  # Automated tests
```

## Testing

```bash
pytest tests/test_environment.py -q
```

## Notes On Experimental Features

`adversarial_generator.py` and the RL fine-tuning hooks in `hybrid_agent.py` are
experimental. They are useful as a direction for future work, but they are not
the core claim of the current implementation.
